二、目标架构：不是三块并列，而是“中台单核，两侧供数”

你接下来应该把整个系统收成下面这个运行关系：

第一层：Simulation Layer（仿真层）
只保留三类职责：
1）用户行为模拟；
2）平台官方 API 仿真；
3）平台回调 / 异步推送 / 错误注入 / 状态推进。
它只产出“平台事实”和“用户行为事实”，不再承担业务聚合、统一查询、推荐生成、规则判定。这个定位和仓库 README 对 User Agent、official-sim-server 的原始定义是一致的。

第二层：Domain Service（中台）
它要成为唯一业务入口。对前端、AI、测试脚本、联调方来说，都只打中台 API。中台负责六平台 provider 编排、统一模型、统一上下文、统一规则、统一推荐、统一会话状态机、统一分析、质检、风控。现在仓库里虽然有 domain-service 目录和 UnifiedOrder 模型，但业务服务层还没长出来，所以这一步是主工程。

第三层：ERP Layer（Odoo）
它只提供库存、商品、销售订单、发货、异常、审核这类 ERP 事实。Odoo 不做客服逻辑，不做规则决策，也不做会话理解。Odoo 数据最终都要被中台吸进来，变成 BusinessContext 的一部分。Odoo 官方文档明确支持通过 CSV/XLSX 导入订单、产品等业务对象，并支持用 External ID 重建对象关系、一对多订单行等结构，所以这层完全可以后补。

三、详细改造计划：按 6 个工作流推进，而不是按目录硬拆
工作流 A：先把“业务入口”从 sim 收回中台

这是第一优先级，因为它决定主角到底是谁。

现在 official-sim-server 还暴露了 /official-sim/query/orders/{order_id}、/orders/{order_id}/shipment、/orders/{order_id}/refund，而且 /official-sim/unified/run 也还在 sim 服务里。这些都应该迁到 domain-service。改完之后，sim 层只保留 run 生命周期、advance、artifacts、push、inject-error、官方 mock 查询；中台新增自己的业务 API，例如：

GET /api/orders/{platform}/{order_id}
GET /api/shipments/{platform}/{order_id}
GET /api/after-sales/{platform}/{after_sale_id}
GET /api/conversations/{platform}/{conversation_id}
GET /api/context/{platform}/{biz_id}
POST /api/recommendations/reply
POST /api/recommendations/action
POST /api/quality/check
POST /api/risk/check
POST /api/integration/refresh

这样改完之后，sim 只提供原始事实，中台提供解释后的业务语义。 这是整个重构的主线。

工作流 B：把“User Agent / Platform Agent”从业务逻辑中剥离出来

README 里已经把 User Agent 定义为“把用户意图翻译成官方 API 调用”，ai-orchestrator 目录里也已经有 api / graphs / nodes / prompts / services / tests，所以你的方向本来就不是错的。现在要做的是再进一步收紧边界：
ai-orchestrator 里保留三个 agent 角色：

user_simulator_agent：生成用户消息、情绪、意图、追问、催单、投诉、退款诉求；
platform_event_agent：生成平台侧异步通知、回调、状态变化、超时、物流签收、拒收、退款进度；
conversation_replayer_agent：把上述行为按时间轴 replay 到 sim。

但要删除或迁出里面任何“统一上下文拼装”“业务规则判断”“赔付建议”“售后结论输出”的能力；这些一律放回 domain-service。Agent 只产生行为，不给业务答案。

工作流 C：把中台补成真正的服务层

现在 domain-service/services 基本是空的，所以中台必须一次性补出“服务骨架”。我建议至少拆成下面 9 个服务：

PlatformGatewayService：统一调度六个平台 provider；
OrderDomainService：统一订单查询/解释；
ShipmentDomainService：统一物流查询/解释；
AfterSaleDomainService：统一售后/退款查询与归一；
ConversationDomainService：统一会话/消息/会话状态机；
BusinessContextService：把平台数据 + Odoo 数据聚成业务上下文；
RecommendationService：输出动作建议与回复建议；
QualityService：质检评分、话术规范、时效质检；
RiskService：风险标签、升级建议、异常流转。

这一步做完后，中台才会从“统一 DTO 层”升级成“统一业务层”。

工作流 D：六个平台统一补齐，不是简单复制三份 adapter

六平台全覆盖不能靠六份 if/else，而是要先立一个能力注册表。
我建议在中台建：

其中 PlatformCapabilities 决定每个平台支持哪些对象：

企微客服：会话 / 消息 / 客服接待 / 用户画像，不强行要求订单。

这样才能既做到六平台全接入，又不把企微硬做成电商订单平台。你现在仓库里六个平台 provider 目录已经都在，但 adapter 还只看到淘宝、抖店、企微三类，所以这一步的重点不是“再加目录”，而是把中台契约补齐。

工作流 E：每个平台都要改什么

淘宝：已有 adapter，重点是把订单/物流/退款/会话的统一查询入口迁到中台；sim 只保留淘宝状态机、fixture、推送、错误注入。淘宝现在最适合拿来做“模板平台”。

抖店：已有 adapter，改法和淘宝一样，但要把平台特有状态码、售后原因、物流字段全部收进中台 normalizer，不要让 sim 或 prompt 层解释字段。

京东：provider 目录已存在，但中台 adapter 侧没看到专门实现，所以要补 JDAdapter、JDProvider、JDStatusMapper、JDErrorNormalizer、JDConversationBridge（如需要）。这是六平台补齐的第一块硬缺口。

小红书：同理，provider 目录已在，但 adapter 缺口仍在。要补 XhsAdapter、XhsProvider、状态映射、售后映射、用户对话桥接。小红书最好把“内容场景触发咨询”也算进上下文。

快手：同理，补 KuaishouAdapter、KuaishouProvider、物流/售后映射、会话能力桥接。快手和抖店可以共享一部分直播电商语义，但不要直接共用状态码映射。

企微客服：它不是订单平台，所以这里不要做“伪订单能力”，而要把企微做成中台的会话主通道：客户会话、客服席位、转人工、接待状态、消息事件，都在中台统一后进入 BusinessContext。企微 adapter 已存在，所以这里主要是把会话状态机和升级流从 agent/sim 迁回中台。

我建议 BusinessContext 至少包含：

这样一来，AI 不再直接读淘宝/抖店原始字段，而是读中台沉淀后的上下文。前端也不用自己拼订单、物流、售后、库存。这个对象一旦立起来，你整套系统就从“多平台数据拼盘”变成了“中台语义层”。仓库里已经有 UnifiedOrder 这种基础对象，但还没有完整的服务化上下文层，所以这是你从 MVP 到可用版最关键的一跳。

四、Odoo 怎么办：没有真实数据时，别等真实库，直接做“数据三层拼装”

你问到 Odoo 现在没有数据，我的建议是：不要等真实 ERP 数据，直接做一套可导入、可生成、可复现的开源数据方案。

最稳的做法不是只找一个“现成 Odoo 数据集”，而是做三层拼装：

第一层，拿 Odoo 官方 demo 当“字段真相”。
Odoo 官方仓库里本身就有 demo 数据：addons/sale/data/sale_demo.xml 里有大量 sale.order 和 sale.order.line；addons/sale_stock/data/sale_order_demo.xml 里不仅有销售订单确认，还会写 stock.picking 的发货计划时间，并给 stock.quant 写库存；addons/stock/data/stock_demo.xml 里也有初始库存量。这些文件最有价值的地方不是量大，而是字段关系和业务对象是 Odoo 原生语义。

第二层，拿 OCA 模块当“异常与扩展真相”。
OCA 的 sale-workflow 里能看到 sale_exception、sale_delivery_state 等销售流程增强模块；stock-logistics-workflow 则提供大量库存、物流、批次、退货、分拣、配送相关扩展。它们很适合用来定义你想要的“订单审核快照”“订单异常快照”“发货异常原因”等 ERP 扩展语义。

第三层，拿公开电商数据集当“规模真相”。
如果你只是为了联调，不需要真实业务；但如果你要让中台测推荐、风控、质检、异常聚合，数据量太小不够。这里我建议至少准备两套公开数据源：
一套是类似 Olist 的电商公开数据，已有约 10 万级订单、支付、商品、评论、地理位置等多表关系，适合补电商订单、物流、评价、售后上下文；另一套可以用带有 order_date / shipped_at / sku / qty 的公开订单集做简化履约数据，比如 Mendeley 上的 10 万条南亚电商订单数据；如果你还想做“及时复购”或补货节奏，Instacart 那种三百万级订单、二十万级用户的购物篮数据也很适合生成复购特征。

具体落地时，我建议你不要把这些外部数据直接原样塞进 Odoo，而是做一个 scripts/erp_seed_builder/：

先读取 Odoo 官方 demo XML，抽出你真正要支持的对象模型：product.template、product.product、res.partner、sale.order、sale.order.line、stock.quant、stock.picking、stock.move、crm.tag 或你自定义的异常对象。
再把 Olist / Mendeley / Instacart 这类公开数据映射到这些对象上，生成标准 CSV。Odoo 官方文档明确支持 CSV/XLSX 导入、External ID 关联关系、以及一对多订单行导入，所以这条路线是可行的。
最后产出三批种子文件：
master_data/：商品、客户、仓库、库位；
transaction_data/：销售单、订单行、付款、出库单；
exception_data/：缺货、延迟发货、拆单、退款、拒收、逆向物流。

这样你就不用等真实 Odoo 库，也不用被单一数据集卡死。

如果你问我“最推荐的起步组合是什么”，我的建议是：
Odoo 官方 demo + OCA workflow 模块 + Olist/Mendeley 两套公开数据。
这样既有 Odoo 原生语义，又有订单量级，还能覆盖库存与异常。
