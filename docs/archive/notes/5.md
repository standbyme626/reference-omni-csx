有 after_sale + 有 exception；
ERP provider 返回空时上下文仍可构建。
8）app/services/platform_gateway_service.py

验收标准：

不应只做 provider 直连；必须和 adapter/registry 协同。
平台能力判断、映射转换、not-supported 错误都应通过统一边界处理。
六平台必须都可通过同一网关访问。

通过判定：

PlatformGatewayService 内能看到 registry/adapter 的使用，而不只是 provider_map。
对 wecom_kf 的会话能力、其他电商平台的订单/物流/售后能力，有明确的 capability 分支，而不是 silent fallback。
9）app/services/integration_service.py

验收标准：

文件必须存在并真正承担中台 integration 逻辑。
至少提供：
inventory 查询
order audits 查询
order exceptions 查询
fulfillment 查询
这些逻辑不能继续藏在 sim 层的旧 integration.py 中。

通过判定：

/api/integration/* 路由调用的是这里，而不是直接去调 sim 旧代码。
相关 service 测试覆盖 mock Odoo 和空数据场景。
D. apps/domain-service/app/adapters/ 组
10）app/adapters/registry.py

验收标准：

不能只是“容器定义”，必须有默认启动入口，例如 bootstrap_default_registry()。
六个平台 adapter 必须全部默认注册。
capability 信息必须和 adapter 注册在同一启动流程里完成。

通过判定：

搜索能看到六个平台名称都被注册。
测试里能断言 registry 对六平台都返回 adapter。
wecom_kf 走 conversation-first，其他五个平台走 order/shipment/after-sale-first。
11）六个平台 adapter 文件

验收标准：

每个平台至少有：
adapter
mapper
status mapper / error mapper（或等价职责）
not-supported 能力要抛清晰错误，不允许返回空对象冒充成功。
映射结果必须统一到 domain-service 的 unified models。

通过判定：

六个平台都各自有测试。
snapshot test 或 fixture-based test 能验证典型 payload → unified object 的映射。
E. providers/odoo/ 组
12）providers/odoo/provider.py

验收标准：

real mode 的契约必须完整，要么统一异步，要么统一同步；不能大量 NotImplementedError 留在运行路径里。
应提供 healthcheck/ping 或等价可用性检查。
mock 与 real 的方法签名必须一致。

通过判定：

所有对外暴露方法在两种 mode 下都可调用。
没有“mock 能用、real 一调用就抛 NotImplementedError”的情况。
13）providers/odoo/mock/provider.py

验收标准：

初始化后至少应包含几组彼此关联的：
inventory
order_audit
order_exception
fulfillment
必须能按 order_id、sku_id 或业务键查到相互关联的数据。

通过判定：

一个订单上下文构建时，能同时读到库存、审核、异常、履约中的至少两类以上数据。
mock provider 测试覆盖：
命中订单；
未命中订单；
新增异常后可回读。

17）根 README 与 sim README

验收标准：

两份文档叙事必须统一：

文档、路由、测试三者一致。
